# Goalventure — Feature Expansion: Supplements, Pantry, Meal Planning, Accountability Partner

## Context

The 9-phase MVP (per `docs/implementation-plan.md`, fully built) covers scheduling, fasting, habit-stack, meal logging, weekly budget, hydration, Travel/Wildcard, and history. The user wants to go further before handing UAT/front-end polish to Codex, driven by their own ideas (a personal "virtual pantry" of ingredients with real nutrition data, drag-and-drop meal planning) plus a formal spec from Gemini that reframes the split as: **Claude builds dynamic, parameter-driven infrastructure; Codex later injects one specific user's real data (weight goals, fasting schedule, supplement doses, partner check-in rules) as UAT seed data** — the same "configuration over hard-coding" law the MVP already follows, just extended to two new domains (supplements, accountability partners) neither of which existed before.

The user separately confirmed a real architectural fork: the accountability-partner feature will be a **real backend with accounts**, not a local-only share mechanism — meaning this repo gains its first server-side component. A location-service reuse question (their existing AI-Mazing-Race app) was investigated and came up empty (private repo, no GitHub access from this environment, and the live app's location features are behind a login WebFetch can't reach) — not blocking, since the user has explicitly deprioritized location work for now; revisit directly if/when we get there.

This plan covers four new subsystems, in the user's priority order for personal excitement (pantry/planning) balanced against build risk (supplements first — smaller, mirrors existing patterns closely, quick win before the bigger pantry/planning arc).

## Locked-in decisions

- **Accountability partner = real backend + accounts** (user's explicit choice over a local-only share mechanism).
- **Backend stack: TypeScript + Drizzle (Postgres dialect) + Fastify + Zod**, new Render Web Service + new Render Postgres, in the **same git repo** under `backend/` (Render `rootDir: backend`) — not a separate repo, not Django/FastAPI like the sibling apps. Reasoning: the endpoint surface is tiny with almost no business logic (heavy frameworks are net overhead here), it reuses Drizzle knowledge just built for the mobile app, and same-repo means the check-in-item/daily-summary payload types can be shared directly between mobile and backend without a published package.
- **Pairing, not email/password auth**: each install lazily creates an `{accountId, accountSecret}` via the backend, stored in SecureStore; short-lived invite codes handle both partner-pairing and multi-device access to one's own account (same primitive, different `purpose`). Real auth (password reset, verification email) is disproportionate infrastructure for a "one user + a handful of partners" system. Tradeoff to accept: losing the only device holding an `accountSecret` before ever linking a second device is unrecoverable — mitigated with a one-time "save this recovery code" screen at account creation, not a full recovery flow.
- **Nutrition data: USDA FoodData Central (FDC)**, free API key via `api.data.gov/signup` (email only, 1,000 req/hour). Client-side key for now (`EXPO_PUBLIC_USDA_FDC_API_KEY`) — the key has no billing behind it, so worst case is quota exhaustion, not cost/data exposure. Migrate to a backend proxy (with response caching) once the accountability backend exists anyway; not a pre-req for shipping Pantry. Open Food Facts (no auth needed at all) is a good later addition specifically for barcode/packaged-goods lookup, not required now.
- **Meal planning: tap-to-assign ships as the permanent, accessible baseline; drag-and-drop is a later, purely additive enhancement on the same write path**, not a replacement. Pure DnD isn't itself accessible (screen readers, switch control), so the tap flow stays in the product regardless of whether DnD ships.
- **Ingredients/meal-preset composition is additive**: a new `isComposed` boolean on `mealPreset` (default false) plus a new `mealPresetIngredient` join table. Existing flat-value presets are completely unaffected — zero migration of existing rows, zero behavior change unless a preset opts in.

## Schema conventions

All new soft-deletable entities use `archivedAt: text('archived_at')` (nullable), matching `dayType`/`mealPreset` exactly — not a new `isActive` boolean convention. All ordering columns are named `order` (not `sortOrder`), matching `routineStep.order`/`mealStackItem.order` exactly. Every new repository imports the client via `@/src/db/client` and gets a real `better-sqlite3` integration test, matching every existing repository.

## New service adapter: `src/services/nutrition-data/`

Exact same shape as `src/services/location-discovery/`: `types.ts`, `NutritionDataProvider` interface (`search`/`getDetail`), `MockNutritionDataProvider`, `UsdaFdcProvider` (USDA nutrient IDs 1008/1003/1004/1005/1079 → calories/protein/fat/carbs/fiber), `createNutritionDataProvider()` keyed off `EXPO_PUBLIC_NUTRITION_PROVIDER` + `EXPO_PUBLIC_USDA_FDC_API_KEY`.

## New domain logic: `src/domain/supplements/timing.ts`

Reconciles a supplement's `timing` flag against `FastingState`/clock time into a checklist item. Pure, unit-tested in Node, same as `fastingState.ts`/`nextStep.ts`.

## Backend (`backend/`, new Render service)

Minimal endpoint surface: `POST /accounts` (lazy creation), `POST /device-link-codes` + `/redeem` (multi-device + partner pairing share one primitive, distinguished by `purpose`), `POST /pairings/invite` + `/accept`, `GET /pairings`, `GET/PUT /check-in-items` (account-configured, never hardcoded field names), `POST /daily-summaries` (upsert `{date, payload: jsonb}`), `GET /accounts/:id/daily-summaries` (self or a confirmed partner). Postgres tables: `account`, `device_link_code`, `partnership`, `check_in_item`, `daily_summary`. Partner-facing view is a simple read-only web page, not a mobile-app install.

## Build order (each phase independently shippable/testable, same rigor as Phases 0–9)

10. **Supplements — core CRUD.** `supplement`/`supplementDose` migration + `supplementRepo.ts`, Settings > Supplements screen. — **DONE**
11. **Supplements — Today integration.** `src/domain/supplements/timing.ts`, `useTodaySupplements`, a Supplements checklist card on Today, take/skip/undo via `onceGuard` + `ensureDailySnapshot`. — **DONE**

    > **Addendum:** `computeSupplementUrgency` deliberately only flags two cases — `fasted` (missed once the eating window opens) and `specific_time` (overdue once its time passes) — because those are the only two timings with a reliable signal to compute from today's data model. `bedtime`/`with_meal`/`pre_workout` always report `'normal'` rather than guessing (no bedtime setting exists yet; no cross-reference between a `pre_workout` supplement and which routine step is "the workout"). Widening this is a natural future enhancement once those signals exist, not a gap in what was asked for now. Dose-taking uses delete-to-revert-to-pending (no stored `'pending'` status), unlike `routineCompletion` which does store an explicit `'pending'` value — a deliberate difference: `supplementDose`'s status enum was scoped to `'taken' | 'skipped'` only in the plan, so "no row" is the only representation of pending, kept consistent throughout the repo/domain/hook rather than introducing a second convention.
12. **Pantry — data model + manual entry.** `ingredient` table + repo, manage-ingredients screen (manual only). — **DONE**
13. **Pantry — USDA FDC integration.** `src/services/nutrition-data/`, search-and-prefill, `.env.example`. — **DONE**

    > **Addendum:** live-verified the actual FDC API shapes before implementing rather than trusting the plan's assumption — a real gotcha surfaced: `/foods/search` and `/food/{fdcId}` return *differently shaped* nutrient arrays (`{nutrientId, value}` flat vs. `{nutrient: {id}, amount}` nested), and at least one real Branded record was observed missing the nested `nutrient` object on its detail response entirely (incomplete source data). `UsdaFdcProvider.getDetail` extracts defensively — a missing/malformed nutrient becomes `undefined`, never a thrown error — which fits the feature's own philosophy: an imperfect imported ingredient is just a starting point the user immediately reviews and can correct, not a value we need to guarantee is perfect. Also fixed a real, unrelated gap while adding `.env.example`: `.gitignore` only excluded `.env*.local`, not a plain `.env` — meaning a real API key placed in `.env` (the standard, expected filename) would not have been protected from an accidental commit.
14. **Pantry — compose meal presets from ingredients.** `isComposed` + `mealPresetIngredient`, live-nutrition query, `foodLog` gains `sourceIngredientId`/`sourceStackId`. — **DONE**

    > **Addendum:** reused the existing `computeStackTotals` (from Phase 4's `mealStack.ts`) unchanged for composed-preset totals rather than writing a duplicate function — the math (Σ calories/proteinG × quantity) is identical, only the file's doc comment was updated to note the dual use. A composed preset's flat `calories`/`proteinG` columns are placeholder zeros (`createComposedMealPreset`), never read; `MealLogGrid`'s `ComposedPresetCard` live-queries `mealPresetIngredientItemsQuery` for both display and the values passed into `logFood`, mirroring `StackCard`'s existing pattern exactly. Also closed a small provenance gap while `sourceStackId` was already being added to the schema: `StackCard` now passes it on log (previously a stack-sourced `FoodLog` row kept no reference to which stack was used, only its combined description text). `sourceIngredientId` is wired into the schema/repo now but has no UI path yet — Phase 15's plan-to-log conversion is what will actually populate it, for a bare-ingredient plan entry with no wrapping preset.
15. **Meal Planning — data model + tap-to-assign.** `mealSlot` + `mealPlanEntry` + repos, weekly grid, tap-to-assign, `convertPlanEntryToLog`. — **DONE**

    > **Addendum:** the "weekly grid" is a day-selector (7 date buttons for the current week) + a vertical list of slots for the *selected* day, not a literal 7-column grid — a dense 2D grid doesn't fit a phone screen usefully, and this is the standard pattern real meal-planning apps use for the same reason. A new "Plan" tab was added (5th tab) since this is a distinct, everyday feature deserving top-level navigation, not a sub-screen of Today or Settings.
    >
    > `mealPlanEntry`'s three-way source (ingredient/preset/stack) resolution — what it displays, its live nutrition, and what gets logged — lives in exactly one place (`useMealPlanEntryDetails`), reused by both the display card and the convert-to-log action, so the two can never disagree. It runs all three possible live-queries unconditionally per entry (rules of hooks; the two that don't apply query id 0, a harmless no-op) — a real, accepted tradeoff: a week with many entries means many simultaneous small queries, fine for a personal-use app's realistic data volume, not optimized further for this phase.
    >
    > `convertPlanEntryToLog` anchors the resulting `FoodLog.dateTime` to noon of the *planned* date, not the moment "Log it" is tapped — a plan entry has no specific time, only a date+slot, and using "now" would misfile a log against today's totals when converting a different day's plan (e.g. logging tomorrow's planned breakfast early, or backfilling a past day). `sourcePresetId`/`sourceIngredientId`/`sourceStackId` (added in Phase 14) get passed through on conversion, so a plan-originated log has the same provenance as one logged directly from Today.
16. **Meal Planning — drag-and-drop.** — **SKIPPED, by explicit user choice**, not an oversight: tap-to-assign is fully functional and accessible on its own, gesture interactions can't be verified from this environment anyway, and this is a good candidate for Codex's later UAT/polish pass. Revisit if wanted.
17. **Accountability — backend skeleton.** New Render Postgres + Web Service (`backend/`), `account`/`device_link_code`/`partnership`, a "Pair with a partner" screen. — **DONE**

    > **Addendum:** `backend/` is an independent Node/TypeScript project with its own toolchain (Fastify + Drizzle/Postgres + Zod + Vitest + PGlite for tests, `tsx` for dev), deliberately not sharing the mobile app's Jest/Expo tooling — it's a separately deployed service, not app code. Route-handler functions are generic over Drizzle's `PgDatabase<TQueryResult, typeof schema>` rather than a hand-defined `AppDatabase` type alias — both the real `node-postgres`-backed instance (`db/client.ts`) and the test `PGlite`-backed instance (`db/testClient.ts`'s `createTestDb()`) satisfy this directly, confirmed by `tsc --noEmit` rather than reasoned out further abstractly. `db` is passed into `buildApp(db)` as a plain parameter, not a Fastify decoration, to sidestep Fastify's module-augmentation ceremony for typing decorated properties.
    >
    > Auth is a bearer credential of the literal shape `"<accountId>.<accountSecret>"` (`requireAccount` in `lib/auth.ts`) — the id so the row can be looked up directly rather than scanning by hash, the secret (SHA-256 hashed at rest, never stored plaintext) to prove ownership. `POST /accounts` returns the plaintext secret exactly once, at creation; there is no recovery flow yet (noted in the plan as an accepted gap, mitigated later by a one-time "save this" screen — not built as part of the backend skeleton itself).
    >
    > `device_link_code` is one primitive serving two `purpose`s (`'device_link'` for attaching a second install to the same account, `'partner_pair'` for accountability pairing) — factored into `services/deviceLinkCodes.ts` (`createDeviceLinkCode`/`redeemDeviceLinkCode`) and reused by both `routes/deviceLinkCodes.ts` (raw create/redeem) and `routes/pairings.ts` (`/invite` wraps create with `purpose: 'partner_pair'` fixed, `/accept` wraps redeem plus the actual `partnership` insert and rejects a redeemed code of the wrong purpose or self-pairing). Redeem-then-mark-used is a single conditional `UPDATE ... WHERE usedAt IS NULL`, so two concurrent redeems of the same code can't both succeed. `partnership.accountId` is the tracked user, `partnerAccountId` the viewer — `GET /pairings` returns both directions (`asTrackedUser`/`asPartner`) since either account might query it.
    >
    > ESLint required its own setup (none existed for `backend/` yet): a plain `typescript-eslint` flat config. Backend's `typescript` devDependency is pinned to `~6.0.3` (matching the mobile app's own pin) rather than left on `^7.x` — `npm install` had resolved TypeScript 7 by default, which `typescript-eslint`'s current release doesn't yet support as a peer (capped at `<6.1.0`); rather than force an unsupported combination, pinned back to a version both tools handle correctly.

Credentials live in a new `src/stores/accountabilityCredentialStore.ts` (Zustand, backed by `expo-secure-store`) — this is the app's first real Zustand usage, since it's genuinely cross-screen session state rather than SQLite-backed data, unlike everything built before it.
18. **Accountability — configurable check-ins + summary push.** `check_in_item` CRUD, `daily_summary` upsert, manual push action. — **DONE**

    > **Addendum:** `check_in_item.key`/`valueType` are immutable after creation (only `label`/`order` can be edited via `PATCH`) — the key is what a `daily_summary.payload` is written under, so letting it change would silently orphan historical data; `valueType` is likewise fixed so an existing key's recorded values can't change shape underneath already-submitted history. Removing an item archives it (`archivedAt`, same convention as the mobile app's soft-deletable entities) rather than deleting it, so past summaries that reference the key stay interpretable. `key` is constrained to `^[a-z][a-z0-9_]*$` since it's a literal JSON object key round-tripped through `payload`.
    >
    > `daily_summary` is one row per `(accountId, date)`, upserted whole via `PUT /daily-summaries` (`onConflictDoUpdate`) — never patched field-by-field, since its `payload` shape simply mirrors whatever `check_in_item`s existed when the client submitted it; the server stores and returns it as an opaque JSON object and never needs to know the item shape (`payload: jsonb().$type<Record<string, boolean | number | string>>()`).
    >
    > `GET /accounts/:id/daily-summaries` authorizes either `id === auth.accountId` (self) or a `partnership` row with `accountId = id, partnerAccountId = auth.accountId` (a confirmed partner) — anyone else gets a 403, not a 404, since the account's existence isn't itself a secret. Defaults to the last 14 days when `from`/`to` aren't given, deliberately echoing the mobile app's own 14-day rolling History window rather than picking an unrelated number. Date-range math uses Luxon (newly added as a backend dependency) for the same DST-safety reasons it's used throughout the mobile app's domain layer, even though this is server-side UTC-only math where it matters less — one less date library to reason about across the codebase.
    >
    > **In-app screens shipped in Phase 20's pass** (see below): `app/(tabs)/settings/accountability/check-in-items/` (list + create/edit-label/archive) and `send-checkin.tsx` (renders each active item as a boolean/number/text input, defaults every field so nothing is submitted `undefined`, `PUT`s the whole payload for today's date). Editing an existing item only exposes `label` in the UI — `key`/`valueType` are already immutable server-side, so the form doesn't pretend otherwise.
19. **Accountability — partner web view.** Read-only web page gated by the partner's `accountSecret`. — **DONE**

    > **Addendum:** served directly from the same Fastify service (`@fastify/static` over `backend/public/`) rather than a separate static site/deploy — one service, one URL, no build step, matching the page's own scope ("glance at today's summary" doesn't justify a frontend framework or a second Render service). It's plain HTML + vanilla JS (`public/app.js`, `index.html`, `partner.html`); DOM nodes are built with `createElement`/`textContent` rather than any innerHTML-with-interpolation, since a `daily_summary` payload can contain arbitrary partner-authored text values that must never be interpreted as markup.
    >
    > A partner has no separate "web account" concept — visiting the page runs the exact same lazy-account flow as the mobile app (`POST /accounts`), just triggered from a browser button instead of app-install onboarding, with `{accountId, accountSecret}` kept in `localStorage` rather than SecureStore. This reuses Phase 17's pairing/auth primitives unchanged rather than inventing a second auth scheme for the web — the same invite-code flow (`POST /pairings/accept`) that would pair two mobile devices pairs a partner's browser instead.
    >
    > Rendering real labels (not raw `payload` keys like `water_100oz`) needed one small addition beyond what Phase 18 shipped: a partner could read a tracked account's *summaries* but had no way to read their check-in-item *definitions* (label/valueType) to render them meaningfully. Added `GET /accounts/:id/check-in-items`, authorized the same way as `GET /accounts/:id/daily-summaries` — which prompted factoring the shared self-or-confirmed-partner check out of `dailySummaries.ts` into `canViewAccount()` in `lib/auth.ts`, now used by both routes rather than duplicated.
    >
    > **Verification limit, same as noted for drag-and-drop in Phase 16:** the full pairing → check-in → web-view loop is exercised end-to-end by Vitest (`app.test.ts` confirms the static pages/assets are served; the route tests cover every API step including a confirmed-partner read and a stranger's 403), but an actual browser click-through wasn't possible from this environment — no local Postgres to run the dev server against, and the deployed instance is still blocked on `DATABASE_URL` (see Phase 17's addendum). Worth a real click-through once the backend is live.

20. **Codex UAT gap-fixes + Phase 17/18 mobile UI.** Triggered by Codex's first UAT pass against a real seed profile (265lb→<200lb, the actual Mon/Wed/Thu/Fri 16/8 + Tuesday 24hr + Saturday Travel + Sunday Game Day schedule) surfacing real gaps before Claude's infrastructure was otherwise "done." — **DONE**

    > **Profile fields:** `userProfile.alcoholRule` existed in the schema since the original MVP but was never exposed by `UserProfileInput`/onboarding — a real oversight, now fixed. Added two new free-text columns, `healthFocus` and `palateNotes` (e.g. "shoulder/back stability, vascular recovery" / "simple/repeatable: chicken, beef, potatoes") — plain nullable text, no enum, per the same configuration-over-hard-coding law as every other field. Also added the post-onboarding editor Codex flagged as missing (`Settings > Profile`) — onboarding could set these values once but never edit them again.
    >
    > **Weight/calorie "ranges" — evaluated, not implemented:** Codex's UAT also flagged that "below 200 lbs" and "0–200 kcal" are ranges/constraints while the schema stores single numeric targets. On review this isn't a real gap: `targetWeight` as a single threshold already captures "get below X" for a personal tracker (the direction is implied), and a hard-fast day's calorie ceiling is already exactly what `dayType.calorieTarget` represents for that day type. Adding min/max fields would be speculative complexity with no behavior change — skipped deliberately, not missed.
    >
    > **Supplement twice-daily dosing — resolved as a seeding technique, not a schema change:** `supplementDose`'s one-row-per-`(supplementId, date)` constraint blocks logging e.g. Omega-3 at both 8am and 3:30pm under a single "Omega-3 Fish Oil" entry. Rather than widen the schema (which would ripple into `buildSupplementChecklist`'s single-status-per-day model), the resolution is to seed it as **two separate `supplement` rows** — "Omega-3 Fish Oil (AM)" and "Omega-3 Fish Oil (PM)" — each independently completable once daily. Nothing prevents this today; it just wasn't obvious from the spec. This is the guidance to hand Codex for re-seeding, not a code change.
    >
    > **`activity_log` and range-based targets remain out of scope** — the former is a pre-existing, already-documented MVP gap (see `docs/implementation-plan.md`'s Phase 9 addendum), not something Phase 17-19 was meant to cover; revisit only if asked.
    >
    > **Phase 17/18 mobile UI:** built `src/services/accountability/` (interface + `MockAccountabilityClient` + `RealAccountabilityClient`, exact same interface+mock+factory shape as `location-discovery`/`nutrition-data`, keyed off `EXPO_PUBLIC_ACCOUNTABILITY_PROVIDER` + `EXPO_PUBLIC_BACKEND_URL`) and `src/stores/accountabilityCredentialStore.ts` (Zustand + `expo-secure-store` — the app's first real Zustand usage, since a bearer credential shared across several Settings screens is genuinely ephemeral cross-screen session state, unlike everything else in the app which is either SQLite-backed or local to one screen). Four new screens under `Settings > Accountability`: the pairing hub (create account, generate/accept invite codes, both pairing-direction lists), check-in item CRUD, and the today's-check-in composer. `MockAccountabilityClient` is a genuinely stateful in-memory simulation (unlike the other two mocks, which are stateless fixture lookups) — pairing/check-ins can't be usefully mocked without *some* memory, so it's the one adapter where that tradeoff was worth it. Unit-tested (`MockAccountabilityClient.test.ts`); `RealAccountabilityClient` isn't (same as `UsdaFdcProvider` — no test exists for the real, network-backed provider, only its mock).
    >
    > **A real, unrelated bug found and fixed along the way:** `backend/tsconfig.json` had no `exclude` for test files, so `npm run build` (`tsc`) was compiling `*.test.ts` into `dist/` alongside real source — harmless to the running server, but it silently doubled Vitest's test count (29 → 58) once a stray local `dist/` existed, since nothing excluded `dist/**` from test discovery either. Fixed with a `tsconfig.build.json` (extends the base config, excludes test files) wired into the `build` script, plus a defensive `exclude: ['**/dist/**']` in `vitest.config.ts` so the same class of bug can't quietly recur.
    >
    > **Expo web-worker bundling issue — investigated, not reproduced, deprioritized:** Codex's UAT reported Metro failing to emit `expo-sqlite/web/worker.ts` under the live dev server, blocking full browser UAT. Re-ran `npx expo export --platform web` after every change in this phase (as always) and it continues to succeed cleanly with zero errors — strongly suggesting the failure is specific to `expo start --web`'s live dev server actually executing expo-sqlite's web WASM backend in a real browser, a code path static export never exercises. Web is not this app's shipping target (iOS/Android are), so this is left for Codex to chase down if/when real browser UAT matters, rather than invested in here.

## Verification

Every phase: `npm test`, `npm run typecheck`, `npm run lint`, `npx expo export --platform web`, then a commit. New repo/domain code gets the same real-SQLite integration-test treatment as existing repos. Backend (`backend/`) has its own equivalent suite (`npm test`/`typecheck`/`lint` from inside `backend/`), run independently since the two projects share no build step or test runner. Manual on-device/in-browser checks remain the honest limit of verification from this environment (drag-and-drop, a full account-pairing round trip against the live deployed backend, and any live-dev-server-only behavior like the web-worker bundling question above).
